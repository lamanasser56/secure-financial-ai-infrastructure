## External prerequisites and trust boundaries

The operator must select a project and pre-existing `me-central2` Artifact Registry standard Docker repository with immutable tags. `artifactregistry.googleapis.com`, `iamcredentials.googleapis.com`, and `sts.googleapis.com` support the release identity path; `dlp.googleapis.com` is needed only for a later synthetic live run. Verify any GKE, logging, or registry API prerequisites against the target environment before enabling anything. This repository does not enable APIs or create identities. Budget, quota, image retention, log retention, and a maximum one-Job run must be approved before spending.

The intended GitHub WIF provider accepts only this exact repository, `lamanasser56/secure-financial-ai-infrastructure`, the `.github/workflows/release-google-sdp-evaluation.yml` workflow on `refs/heads/main`, and the `workflow_dispatch` event. The provider should bind immutable GitHub repository identity claims where supported; check current GitHub claim values before creating the binding. A protected `google-sdp-evaluation-release` environment must have independent review and restrict main. Configure the WIF provider name, release service-account email, and project ID as GitHub environment variables named `GOOGLE_SDP_RELEASE_WIF_PROVIDER`, `GOOGLE_SDP_RELEASE_SERVICE_ACCOUNT`, and `GOOGLE_SDP_RELEASE_PROJECT_ID`. They are names, not credentials. Never use JSON keys, stored OAuth tokens, or a credential file in the Docker build context.

Grant the release identity only the verified repository-level Artifact Registry permissions needed for Docker push and repository metadata read; Google's `roles/artifactregistry.writer` is a candidate to verify before binding. WIF service-account impersonation requires the documented `roles/iam.workloadIdentityUser` binding for the exact trusted principal; confirm the principal syntax from the actual pool/provider configuration. Do not grant project-wide Owner/Editor. GKE uses a separate dedicated `google-sdp-evaluation` KSA and GSA boundary. Its narrow Google SDP role candidate is `roles/dlp.user`, subject to official permission verification and target review. GKE nodes need verified image-pull rights independently of the Job KSA. These are future operator actions, not implemented grants.

## Manual release and evidence

After gates 1 and 2, dispatch the workflow on main with the reviewed full commit SHA, region `me-central2`, existing immutable-tag repository name, and image name. The qualification job has no Google token permission and runs tests, lock checks, source lint, an offline deterministic image build, SBOM, Trivy, and the unchanged HIGH/CRITICAL policy. The publish job first reproduces the same image configuration ID, then uses GitHub OIDC and WIF to obtain a short-lived Google access token without writing a credential file. It checks the repository's immutable-tag setting before push. The commit-derived tag is only a staging address; the workflow records the resolved registry manifest digest and uses that digest for fresh scan, SBOM, policy, signing and verification. The local image ID and remote manifest digest are distinct identifiers; equality is not assumed. Review all uploaded evidence before accepting gate 4. A passing signature does not establish real-world detection accuracy or provenance beyond the verified workflow identity and source controls.

If registry scanning or signing fails after push, quarantine or remove the unsigned digest and its tag using a separately authorized cleanup process. Do not deploy it. Review CISA KEV and vulnerability database timestamps at release time. Retain only approved sanitized evidence for the approved retention period. No access token, OIDC token, request text, provider response text, or raw fixture output belongs in an artifact.

## GKE execution and containment

The unapplied Kustomize package is separate from `kubernetes/base`. The renderer requires project ID, matching GSA email, and an exact `me-central2-docker.pkg.dev/...@sha256:` image reference. It writes only a temporary manifest, validates it, and has an explicit cleanup command. Before any later apply, confirm signature and exact digest, target GKE Pod Security Admission, Workload Identity binding, DNS and metadata server variants, resource quota, Job TTL support, and log access. The Job's only request path is the fixed `dlp.me-central2.rep.googleapis.com` endpoint, with `--live` and the exact synthetic-only acknowledgment. It contains no LiteLLM request and no change to the Presidio runtime.

Kubernetes NetworkPolicy cannot enforce an FQDN destination. The Job policy denies ingress, scopes DNS and GKE metadata traffic, and permits public TCP 443 outside private/link-local ranges. That is not proof of regional egress containment. Require separately reviewed DNS and FQDN-capable egress enforcement or equivalent target controls before a live run; if unavailable, do not run. Check the target CNI and NodeLocal DNS path with a disposable synthetic test. No customer, production, real financial, or uncertain identity data may be sent.

After a separately approved bounded run, capture only schema-valid sanitized result JSON, status, timing and estimated cost. Delete the temporary render directory, Job/Pod and any unneeded registry image by an approved cleanup procedure, and verify logs and artifacts against retention rules. Record **PASS FOR FURTHER BOUNDED INTEGRATION**, **FAIL AND RETAIN PRESIDIO**, or **INCONCLUSIVE — MORE EVIDENCE REQUIRED**. None authorizes Presidio deletion or a provider-authority change.
