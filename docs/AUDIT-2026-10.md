Audit date: **25 October 2026 (Asia/Riyadh)**. Audited source: **`1d7dcc33f00b22b26a21e81cb69d24342824fd0f`** (`main` at audit start). Assessment source: `41ffbf260a446b5db2292356a8ea23219e58a524`. This document is the only repository change in this audit branch. It is an engineering review and proposed work, not authorization to change infrastructure or a new live security result.

## Release decision

**The repository is not ready for a clean, single-source release.** The current deployment deliberately combines older service images, four assessment-era application images, current manifests, and executable programs mounted from the checkout. Green source CI does not establish that this combination is the exact assessed release. There are also independently reproducible renderer, reset-command and posture-check defects.

Keep the existing evidence immutable. Repair the current implementation and release process, then qualify a new, completely identified release. Do not rewrite old evidence to make it appear current; do not remove fail-closed controls merely to make refactoring pass.

## Method, confidence and coverage

The review inventoried **627 tracked leaves**. All tracked text was scanned for references, build inputs, image pins, historical hashes, exceptions, transforms and deferrals. Python source was parsed for imports, definitions and static reachability; duplicate bytes were compared. Production entrypoints, Docker COPY/ignore boundaries, Make targets, CI jobs, manifest generators, Terraform roots and each finding below were traced manually. Appendix C records every audited leaf. Binary screenshots and font assets were inventoried and hashed, not treated as executable code or re-rendered.

Only local, offline probes were used: Kustomize with synthetic configuration, renderer invocation without a release lock, AST comparisons, and posture evaluation against a fake client populated with the committed RBAC. No cloud API, deployment, image build, scanner refresh, live model/DLP call, teardown, UI edit or application change was performed. Existing evidence was read as historical evidence, not independently reverified. CI may run its normal PR checks on this documentation branch; no release workflow was dispatched.

“Dead” below means unreachable from the declared product entrypoints or referenced only by tests/history in this tree. It is not a mathematical proof of absence of reflection or external consumers. Optional CLIs that are still executable are called **orphaned/legacy**, not dead. Runtime reachability was rooted in App, gateway boundary, Ops server/executor, bootstrap, fault demo, mounted gateway/redactor programs, Financial frontdoor/worker and its server handlers; Node entrypoints and build-time indexing were inspected separately.

Effort is engineering effort before full live qualification: **S** roughly 0.5–2 days, **M** 3–5 days, **L** more than a week or several coordinated changes. Risk describes the present engineering/release risk, with migration hazards stated in the fix. **Yes** blocks the requested clean release; **Scope** blocks an affected advertised guarantee or retained feature, otherwise requires an explicit narrower scope; **No** is maintainability work that can be intentionally accepted. These are not claims that every item is an exploitable vulnerability.

### Final immutable sequence

1. Close blocking findings, record accepted narrower-scope limitations, and pass the complete offline/packaged integration suite. Freeze `main` at **commit C**; protect it from further source/config changes during qualification.
2. **Build all seven first-party release images from C**, with pinned external bases and declared materials. Scan every final digest under the unchanged policy; create SBOM/provenance, sign and verify exact identities, and create/verify admission attestations. Stop on new disallowed findings; do not expand exceptions to force a release.
3. Generate one immutable release manifest **R** containing C, every digest, configuration/policy hashes, migration version, build/scan/signature/provenance references and assessment profile differences. Store R as a signed artifact or metadata-only release record. Avoid the impossible requirement that a commit contain its own future digest or that updating image pins silently trigger a second build.
4. **Run the full live assessment on exactly R's images and configuration**, with independent cleanup controls and an explicit bounded-provider plan. Stub-mode results and real provider checks have separate scope. No rebuilding, retagging to a different digest, source mounts or unrecorded manifest repairs during the run. Any material fix invalidates that candidate: create C2, rebuild the affected complete release set and rerun required full qualification.
5. Publish the complete sanitized verdict and release receipt. **Deploy exactly R**, using the same release-aware staged renderer; read back running digests, configuration, migrations, signatures/attestations and readiness. Run final smoke/demo checks and record the map screenshot against R. If promotion metadata is committed afterward, it changes no build input and does not claim that the images were built from that later metadata commit.

The requested endpoint is therefore: **freeze main → build all images from that commit → full live assessment on exactly those images → deploy those images**. Teardown is a separate, later authorized operation.

## Appendix B — retained boundaries and dead-code decisions

The following are not to be deleted as “wrappers” merely to reduce file count:

- Gateway boundary, trusted Financial frontdoor/data broker, per-user worker isolation and independent Ops executor: these deliberately separate authority. Their contracts and packaging need cleanup; the privilege separation is valuable.
- `boundary_http` transport limits, no-redirect handling, bounded redactor workers, fail-closed admission and explicit no-retry budgets: security controls, not historical clutter.
- SQLite replay consumption before mutation: a durability boundary, distinct from stdout audit. Rename/document it accurately rather than removing it.
- Generated agent/provider manifests: acceptable checked build outputs when a single generator owns them and drift checks exercise current behavior. Avoid hand-edited second definitions.
- Font copies in two final images, separate Terraform provider lock files, small identical input schemas, empty `__init__.py` files and repeated before/after evidence ledgers: duplicate bytes alone are not defects. The issue is multiple hand-maintained authorities, not repeated storage.
- Historical evidence, failed/blocked experiments, scan reports and screenshots: preserve immutable originals. They become debt only when current runtime or release checks depend on them as current authority.
